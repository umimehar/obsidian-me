# 2026-08-24

Four items off the post-phase-3 list. 1207 tests to 1221, three commits, and `scripts/` is gone.

## RoomBar announced 47% for 46.641% and 25% for 24.921%

The seventh and eighth instances of this project's most-repeated defect, and both were live on screen since phase 2c.

Radix's `Progress` derives `aria-valuetext` from its own value and rounds to whole percent. Confirmed in Chromium before touching anything: `aria-valuenow="46.64179104477612"` beside `aria-valuetext="47%"`. The 2025 line does the same, 24.921% announced as 25%.

What makes it the clear case rather than the arguable one is that **no percentage is printed anywhere on either card**. The money is, in full: `$33,000.00` contributed, `$37,752.00 remaining of $70,752.00`. So a sighted reader never had the percentage either, and the announcement was the only place it existed. No reader could have caught the drift by looking.

`ShareBar` had already faced this exact defect and ruled on it: an explicit `aria-valuetext` only helps where the assistive technology honours it over `aria-valuenow` and `aria-valuemax`, and where it does not the same share is recomputed back to a whole percent. Defending a precision rule with an attribute whose precedence is an implementation detail is not defending it. That ruling never propagated to `RoomBar`, so the fix is to reuse `ShareBar` rather than add a second decorative bar.

**The `aria-valuetext` was the only pin on the fill's magnitude.** Removing it naively would have left an inverted bar shipping green, so the width is now pinned at both real shares, plus the clamp at over-limit and the zero-limit branch, neither of which had ever been covered. Five assertions keyed on `role="progressbar"` would have become permanently un-failable once the role went, and are re-keyed to the bar that actually renders.

Mutation audit: nine constructed, nine reddened. The two that matter are not the arithmetic ones. `M8` gives the bar back a role and `aria-valuetext="47%"`, the defect literally returning, and reddens 10 tests including the new sweeps on both the wrappers tab and the registered view. `M9` puts a percentage on a `title` attribute of a different element, a genuine second rendering path rather than the shared `share` variable, and reddens 3.

One methodological note. `M8` first ran as a no-op because `${Math.round(percent)}` interpolated in **perl**, not in the template literal, so the edit failed to apply. The script flagged it invalid instead of scoring it as a kill. Third time on this project a mutation has quietly tested something other than what was intended, and the guard is worth keeping: assert the mutation is present in the file before trusting its result.

## The contrast gate could not see what it was passing

`bun run contrast` reported AA pass for a whole phase while structurally blind to two things. It sampled the text present at sweep time and never hovered, so **no chart readout had ever been measured**, before or after any change to one. And it opened only the default lens of a three-lens view, so the loss colour was never swept.

It now hovers every chart on every tab and visits the account and purpose lenses. Samples carry the state they were taken in, so the summary shows what was reached rather than folding every state into one healthy-looking tab total.

**My first version repeated the same mistake one level down.** Only `hover chart 1` appeared in the output, on every tab, though growth has 20 charts. The pointer only moves within the viewport, so every chart below the fold was unreachable and the loop was measuring the portfolio chart above the tab strip over and over while still reporting a clean hover sweep. Scrolling each chart into view first fixed it.

Verified by instrumenting the gate rather than trusting the state labels: **78 loss-coloured runs measured**, the two real ones at `-$3.16` and `-$45.04` in `lens by account`, ratio 5.20, red on white. **236 tooltip runs measured**, tightest 5.94. Both pass AA, and both were previously outside the sweep entirely.

Two guards added, because a sweep that reaches nothing must not read as a pass: the run fails outright if no readout is measured anywhere, or if fewer lenses are swept than exist.

3606 runs of text now, up from 2876. That baseline was measured by running the gate at the parent commit, after I had written an estimate into a commit message and had to correct it.

## The auto-backup captured this work anyway, and the setting change was not enough

Turning off `autoBackupAfterFileChange` was item 1 and it is done. It did not stop the ninth capture: commit `385003c "vault backup: 2026-08-24 17:42:17"` swept the whole deletion, both doc rewrites and the `.gitignore` edit into a generic backup commit, **and pushed it to origin/main**.

`autoSaveInterval: 15` is a separate trigger. The file-change trigger and the interval trigger are independent, and disabling the first leaves the second committing and pushing every fifteen minutes. Nothing was lost and the commit contained only this endeavor's files, verified before touching it, but the deletion now sits in shared history under a message that says nothing about it.

The commits were already pushed, so history was left alone rather than rewritten. This entry is the record of what `385003c` actually contains.

The mitigation that does work is the one already known: commit early and often. Both earlier commits survived with real messages because they were made before the interval fired.

**Both triggers are now off.** `autoSaveInterval` set to 0 on 2026-08-26 alongside the earlier `autoBackupAfterFileChange: false`. `autoPullInterval: 5` is left on, since pulling does not commit.

## Reviewing my own work found a hole in my own guard

The two guards added to `run.ts` had never been demonstrated to fire, which is this project's own definition of not a check. Testing them found a real defect in one.

The missed-lens guard recovered the lens list by string-matching the state label **it had itself written** (`state.startsWith("lens ")`). A guard that reads a label it also writes is measuring its own formatting, and it is the same load-bearing-string pattern phase 3 task 5 rejected for `ProjectionYear.notes`. Each lens now records itself in a set, and the message names the lens that was missed rather than counting to two.

The bigger hole was underneath it. That guard proved a lens sweep found **text**, not that the lens ever **changed**. A click that silently failed would have swept the default lens a second time under a lens label, counted as covered, and hidden the loss colour exactly as before, which is the original bug wearing the guard as a disguise. The lens is now asserted to have become the selected one, the same way `applyTheme` already proved the theme took by reading the page's own background back. That pattern was sitting in the same file the whole time.

Four guards, each demonstrated to exit 1 with a message naming the real cause: a renamed tooltip selector, a lens dropped from the list, a click that does nothing, and a readout leaking between charts. Clean run unchanged at 3606 runs, AA pass.
