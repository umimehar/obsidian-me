# 2026-08-19

## Phase 3 built

Eight tasks, 28 commits, 1054 tests to 1158. Goal tracking and room runway both render inside the Projections tab, reading the rows `projectYears` already returns. Tracked as TCK-0001 on the central board, the first ticket this vault's orchestrator has carried.

Goals are declared in `app/src/goals/config.ts`, owner-reviewed the way `LABELS` and `PURPOSES` are, and a goal can scope to the whole portfolio, to registration groups, or to a purpose tag. Two ship, both with statutory targets: the FHSA's $40,000 by 2028 and the RESP's $50,000 by 2042. No retirement or growth goal ships, because a goal card renders a verdict and nobody supplied a target, so inventing one would manufacture a verdict.

The runway table carries six bounds. The one worth having built it for: **CESG tops out at $6,650 against its $7,200 cap**, because the beneficiary ages out in 2042 before the contributions that would claim the rest. $550 is forfeited, and a table reporting only "CESG ends 2042" would have hidden that entirely.

`bun run contrast` passes AA in both themes, worst light 4.67, worst dark 7.50.

## The rate moves one feature and not the other

A survived mutation proved the design spec wrong. It claimed every runway year moves with the rate, because a higher return fills a lifetime cap sooner. It does not. A contribution cap is consumed by contributions, not by growth, so a portfolio compounding faster does not use its RESP room any sooner. Measured at 0%, 6%, 12% and 25%, every runway year is identical, and a reviewer went further and proved it structurally: no contribution step in `engine.ts` reads a balance at all.

So goals re-judge live when the slider moves and the runway holds still. That is a real difference between two features on one page, and it is now stated rather than implied. The false claim had already reached a doc comment before it was caught.

## What the browser found, and what it did not

Three things happy-dom cannot settle were settled in Chromium against the real accessibility tree. Both goal cards expose their composed name on `role="group"`, which retroactively confirms that ARIA's ban on naming `role=generic` was the right diagnosis and that adding the role was not superstition. `Table.RowHeaderCell` does surface as a genuine `rowheader`. And the rate slider's real arrow-key path announces `aria-valuetext` matching the visible label character for character at 6.25%, 25% and 0%.

The amber shortfall states were measured rather than computed, at 4.61 against a 4.5 floor. They had to be forced through a test seam, because both shipped goals are ahead of target at every rate the slider offers, so no default pass ever paints them.

No defect was found in that pass. Declared unverified: no real screen reader was run end to end, and no touch viewport was checked.

## Three lessons, all in knowledge/lessons.md

**An absence assertion keyed to a truncation cannot fire when rounding goes up.** The test guarding this project's most-repeated defect could not catch it: it looked for `$92,547` as the coarse form of `$92,547.67`, which actually rounds to `$92,548`. Different digits. Its sibling assertion worked only by the luck of `.10` rounding down. The founding instance of the defect, `$241,740` against `$241,739.67`, was itself a round-up, so the guard would have missed its own ancestor.

**Mutating a shared variable proves the variable is used, not that two renderings agree.** An audit reported "6 of 6 figures caught" having mutated six variables and zero second-path renderings, which is the only place this defect has ever actually lived.

**`git checkout --` restores to the last commit, not to the previous moment**, so it silently discards uncommitted work along with the mutation you meant to revert. Caught only because the restore was checked by checksum rather than exit code.
