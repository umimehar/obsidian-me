## The source folder is not uniformly named

The 221-file source folder turned out to hold two filename conventions, not one: 220 files as `<ACCOUNT>_<YYYY-MM>_<TEMPLATE>.pdf` (the bulk-export convention every prior task assumed), and exactly one as `<ACCOUNT>_person-<id>_<YYYY-MM>_v_<n>.pdf` — no template segment at all. That second form is what a statement actually downloads as, one at a time, from the Wealthsimple app. Verified byte-identical (matching sha256) to its conventionally-named twin, so it is the same statement under a different name, not a new one.

Two changes to `source.ts` handle this properly rather than special-casing the one file: `parseSourceFilename` now accepts both forms, returning `templateStated: false` for the fresh-download form since it carries no template to read. And `detectTemplate` reads the template from the document itself, for every file, never from the filename — a PERFORMANCE statement is the only one carrying "Money-weighted Return Rates", a CASH statement calls itself a monthly statement on page one only, and a BROKERAGE statement names itself managed or order-execution-only. Verified against the full 221-file corpus: zero ambiguous or undetected cases. `build.ts`'s `resolveTemplate` always takes the document's answer and warns (never throws) on a filename disagreement, so a genuine future mismatch is visible rather than silently trusted either way.

This is the same lesson the CSV-era pipeline learned the hard way, twice: classifying anything by filename is unreliable, and here it would have been fatal to the whole "drop a fresh statement in and rebuild" workflow, since the single-download form is exactly what an owner would use month to month.

Deduplication is by content hash (sha256 of the file bytes), computed once per file and reused for the same cache key `extractXml` already uses internally. The one duplicate in this corpus was skipped and logged; `ingestAll` returns 220, not 221.

## Two real findings, both resolved without touching a figure

**`d6d9` (RRSP, managed) 2025-11, cross-document.** The account's first-ever statement, funded mid-period with a $12,000 deposit. The PERFORMANCE statement's own summary row reads `$0.00 / $12,000.00 / $0.00 / $0.00 / $11,984.22` for start/deposits/withdrawals/change-in-market-value/end — the printed Change in Market Value is $0.00, but start + deposits - withdrawals + change ($12,000.00) does not equal the printed end ($11,984.22). Traced it to the underlying cash flow: $12,000 in, $11,953.48 spent on securities, $46.52 cash left, and those securities were actually worth $11,937.70 by month end — a genuine $15.78 unrealized loss that Wealthsimple's own Change in Market Value figure fails to capture for a position opened and revalued within the same period. Every number the parser reads is correct; the statement's own report just doesn't reconcile for a mid-period-funded first statement. Acknowledged in `corrections.ts`, not patched in the parser.

**Reconciliation report leaked raw account codes.** `checks.ts`'s `finding()` helper builds `sourceFile` from the pre-mask statement, the same raw filename `buildDatastore` normally strips before anything reaches disk — but `reconciliation.json` was being written straight from `runChecks`'s output, bypassing that step entirely. Caught by hand-inspecting the file rather than trusting the prescribed leak-check grep, which has its own blind spot: `\b(WK|HQ|WZ)[A-Z0-9]{7,}\b` requires a non-word boundary after the account code, but every occurrence here is immediately followed by `_` inside the filename, and underscore counts as a word character to `\b` — so the regex silently passed a file that still had the account code in plain text. Fixed with `maskFindingSourceFile` in `build.ts`, applied to every finding before `reconciliation.json` is written, using the same filename-prefix substitution `buildDatastore` already uses for `source.file`. Mutation-verified: reverting the fix reintroduces the raw account code and the corresponding unit test catches it.

## A second leak, unrelated to code

Inspecting `datastore.json` by hand (not just running the five prescribed checks) turned up a beneficiary's full name leaking through activity descriptions across roughly 14 statements. `redactions.json` listed the first name but not the surname, so `redactText` correctly redacted the first name and left the surname exposed every time. Root cause: the name list was incomplete, not a masking-logic bug. `redactions.json` is gitignored and lives outside version control, so this fix is local to this device only — worth confirming it is reflected wherever else that file is maintained. The postal-code leak check (`\b[A-Z][0-9][A-Z] ?[0-9][A-Z][0-9]\b`) does flag 13 hits in `datastore.json`, all the same match: Deloitte's own Toronto audit-office address, printed verbatim in a year-end "AUDIT NOTE" boilerplate on several statements. Verified by inspection — this is the auditor's public corporate address, not the account holder's, and is not masked.

## Phase 2a: the analytics layer

Seven tasks, 290 tests, `data/analytics.json` generated and committed. It is what the dashboard will read; nothing in the UI re-derives from statements.

The layer's rule is **read what the statement states, derive only what it does not**, and it is why this is simpler than the pipeline it replaces. Contributions are printed on 104 statements (85 as a running year-to-date figure, 19 with the first-60-days split), so a month's contribution is a delta between consecutive stated totals rather than a guess assembled from transaction codes. The old pipeline guessed and undercounted RRSP by $8,000.

Five real defects were caught by checking figures against the real statements rather than trusting a green suite:

- **RESP contributions read as zero.** That account states no contributions block on any of its six statements, while its activity shows $2,550 of CONT and $450 of DEP. Task 3's room and grant lines build directly on this number, so a zero would have made the whole RESP view wrong and plausible. Derived now, grants excluded, and labelled `derived` so it can never render as printed.
- **RESP was given an annual contribution limit it does not have**, reporting remaining −$500. There is no annual cap; the only contribution bound is the $50,000 lifetime figure, and $2,500 is the contribution that attracts the maximum basic annual CESG.
- **TFSA reported remaining −$14,000** against the generic annual maximum. Room accumulates and carries forward, so that is an over-contribution flag by another name. `remaining` is now null on every generic-limit line and populated only where a notice of assessment gives a real figure.
- **Returns mixed units** — stated rates in percent, derived in fractions, in the same field.
- **A derived return of 186% in one month.** A derived return can only subtract flows it can see, and the cash block misses money that does not arrive as cash. Book cost is the discriminator: performance moves market value and leaves book cost alone, while money arriving moves both. Points failing that check return null with a reason instead of a confident number, which removed the three artifacts and kept a genuine 39% month.

Verified figures: 2026-06 market value $241,739.67, identical across all three lenses. RRSP 2026 $33,000 used against an assessed $70,752, leaving $37,752. FHSA $24,000 of the $40,000 lifetime cap. RESP $3,000 of $50,000, CESG $550 of $7,200. 2026 eligible dividends $201.86, and relabelling the corporate account as personal reproduces the replaced system's wrong $645.25 exactly, so that regression guard is real.

Outstanding owner inputs, both defaulting safely: purpose tags per account (everything is `unassigned`, so that lens is one bucket) and account labels (they read `TFSA d77c` rather than a name).

## Owner figure: 2025 RRSP deduction limit, and the $1,000 it exposes

**2025 RRSP deduction limit: $60,191.00**, owner-supplied 2026-08-06, from the notice of assessment. This belongs in `ASSESSED_ROOM` in `app/src/analytics/rooms.ts` as `RRSP: { 2025: 60191 }`, alongside the existing `2026: 70752`. It is not yet added, because adding it changes rendered figures and needs its own tested change plus an `analytics.json` regeneration.

Adding it would turn the 2025 RRSP line from generic to assessed: limit $60,191 instead of the $32,490 annual maximum, `assessed: true`, and a real `remaining` where today it is correctly null.

**The figure does not reconcile with our own 2025 contributions, and it is off by exactly $1,000.**

The 2026 entry is documented as coming from the 2025 NOA: $45,191 unused at the end of 2025 plus $25,561 earned in 2025, giving $70,752. Working backwards, $60,191 assessed for 2025 minus $45,191 left unused means **$15,000 was contributed in 2025**. The PDF pipeline computes **$14,000**: $2,000 in the self-directed RRSP (2318, stated 2025-09) plus $12,000 in the managed one (d6d9, stated 2025-11 as a lump spanning 11 months).

Two independent things point at the same conclusion. The arithmetic closes exactly at $15,000 and misses by exactly $1,000 at $14,000. And the replaced CSV pipeline recorded 2025 RRSP contributions as **$15,000**, noted in the old `CLAUDE.md` ("for 2025 $15,000, $48,000 total") — a figure the rebuild has quietly disagreed with without anyone noticing.

The likeliest location: **2318 states no contributions figure at all for 2025-10, 2025-11 and 2025-12**. Its last stated year-to-date figure is $2,000 at 2025-09, and the series carries `contributions: null` for the three months after it. A $1,000 contribution in that window would be invisible to a delta-of-stated-totals approach, which is exactly how this layer works by design.

Not yet proven, and deliberately not "corrected" in the parser. Next step is to read 2318's 2025-10 to 2025-12 statements directly and check whether any states a contribution the pipeline is dropping. If it does, it is a parser defect. If none does, the money arrived somewhere the statements do not print and the gap belongs in `corrections.ts` with its evidence, per the rule that a genuinely wrong statement stays wrong and visible.

## Phase 2c: charts, navigation, projections

Eleven tasks, 27 commits, 479 tests to 1009. Six tabs synced to `location.hash` replace one 22,000px scroll. Four new charts (returns, contributions against room, monthly cashflow, market against cost), a shared cursor with keyboard and pointer tooltips, and a projections view over the ported engine.

Three real defects in the owner's data came out of it, and none was found by a test.

**$1,000 of RRSP and $4,000 of TFSA contributions were being dropped.** Wealthsimple's dual-currency layout omits the Contributions panel entirely for four months (2025-10 through 2026-01) on three accounts. It returns in 2026-02 and the parser reads it correctly there, so the parser was never at fault. `contributionsByYear` took the year's last stated figure, and anything contributed after it vanished. 2318's October $1,000 and d77c's October $4,000 are both printed on the page, the second one twice. The owner's notice of assessment is what exposed it: $60,191 assessed for 2025 minus $45,191 unused implies $15,000 contributed, and the pipeline said $14,000. After the fix RRSP 2025 reads 15,000 used with 45,191 remaining, matching the figure already written in the 2026 comment. TFSA 2025 moved 21,000 to 25,000, which nobody predicted and which is the strongest evidence the fix was not tuned to hit the target.

**d6d9's stated returns are arithmetically impossible.** One $12,000 deposit at 2025-11, zero flows since, and 2026-03 holds $12,531.01 while stating -0.52% against 2026-04 holding $12,370.86 and stating +10.31%. More money, lower return. Six PERFORMANCE statements read at the source confirmed the parser reads every horizon correctly, so this is Wealthsimple's error and sits in `corrections.ts` with the figures left visible and wrong. A new check flags a no-flow period whose return and balance move apart, gated on two signals that are unsound apart and sound together.

**Three light-theme contrast failures**, at 4.25, 4.28 and 4.43 against a 4.5 requirement, on badges appearing across four tabs. Found by measuring in Chrome, not by reading CSS.

The projection defaults to 6% rather than the 24.84% fitted from 37 months of market value. That fit is arithmetically right and compounds to about $431M over thirty years, so the fitted figure renders beside the default with its window as the caveat and a control to apply it. Un-netted for deposits the same corpus reads 486.85%, which is what the netting is for.

Two lessons worth keeping. Ratio tests cannot catch a uniform scale error, because compressing two marks equally preserves every ratio between them; anchor a mark to the axis instead. And a lesson only propagates forward: `ValueOverTime` shipped able to draw the whole portfolio at half height with 1009 tests green, because its geometry test compared the cursor dot to a vertex on its own line and both move together. Every chart now catches a 0.7 compression.
